## Slide 2 — What I built

- A grounded Q&A API for data-science learners: ask any Python question, get an
  answer cited against real Stack Overflow answers.
- `POST /ask` → answer + cited sources + grounding flag; `GET /health`.
- 30,000 highest-quality Q&A pairs indexed from the 987k-row Kaggle dataset.
- Fully tested: pytest suite (mocked LLM) + 10 documented live queries.

## Slide 3 — Architecture

```text
            ┌───────────────────  FastAPI service  ───────────────────┐
 question ─▶│ validate ─▶ cache? ─▶ embed (MiniLM ONNX)                │
            │   ─▶ ChromaDB top-k (cosine HNSW)                        │
            │   ─▶ relevance gate ─▶ Groq Llama 3.1 8B (async)         │
            │   ─▶ answer + [1][2] citations + sources[]               │
            └──────────────────────────────────────────────────────────┘
 offline:  parquet (987k rows) ─▶ DuckDB: best answer per question
           ─▶ top 30k by votes ─▶ HTML→text ─▶ embed ─▶ persistent index
```

---

## Slide 4 — Key design decisions (1/2): data & retrieval

- **Quality over volume:** one best-voted answer per question, top 30k by score.
  Community votes are a free reranking signal — every indexed answer is verified.
- **Asymmetric embedding:** embed only `title + question` (what user queries
  resemble); store full Q&A text for the LLM. Sidesteps MiniLM's 256-token limit.
- **ONNX MiniLM, no PyTorch:** ~80MB runtime, fits free-tier hosts.

---

## Slide 5 — Key design decisions (2/2): generation & grounding

- **Llama 3.1 8B Instant on Groq:** ~1s end-to-end answers, generous free tier.
- **Grounding contract in the prompt:** cite excerpts inline `[1]`, flag
  unsourced claims, decline non-Python questions, modernise Python 2 answers
  (dataset is pre-2017).
- **Relevance gate:** cosine-distance threshold sets `grounded: false` instead of
  hallucinating when retrieval is weak.

---

## Slide 6 — API design

- `POST /ask` — `{question, top_k?}` → `{answer, sources[], grounded, model, latency_ms, cached}`
- `GET /health` — index size + model (used as readiness probe)
- Pydantic validation (length, top_k bounds) → clean 422s
- LLM failures surface as 502 with detail, never a hang (30s timeout)
- In-process FIFO answer cache (repeat questions are free)

## Slide 8 — Observed behaviour & edge cases

- Strong on canonical questions (reverse a list, dict merge, decorators) —
  answers cite high-vote sources and include runnable code.
- Vague queries ("my code is slow how to make fast") still retrieve useful
  profiling/optimisation threads — answer stays generic but grounded.
- Off-topic ("capital of France") → declined politely, `grounded: false`.
- Known limit: dataset ends Oct 2016 → prompt forces Python-3 modernisation;
  newest features (f-strings, walrus) answered from model knowledge, flagged.

---

## Slide 9 — Scaling to 100+ concurrent users

- **Async everywhere:** non-blocking LLM calls; multiple uvicorn workers behind
  a load balancer; Groq does the heavy compute, app stays I/O-bound.
- **Latency:** dominant cost is the LLM (~1s). Stream tokens (SSE) for perceived
  latency; embed on CPU is ~5ms.
- **Database:** move Chroma → managed vector DB (Qdrant/pgvector) so replicas
  share one index; read-only replicas scale horizontally.
- **Caching:** Redis answer cache keyed on normalised question (high hit rate on
  learner traffic); semantic cache for near-duplicates.
- **Cost:** Llama-8B on Groq ≈ $0.05/1M input tokens → <$0.001 per answer;
  caching + 8B model keeps 100 concurrent users in single-digit $/day.
